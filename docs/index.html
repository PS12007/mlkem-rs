§2

Why a stopwatch is a weapon

Correct output is not enough. If the code takes even a few nanoseconds longer for some secret values, an attacker who can time it, and averages over thousands of tries, can work the secret out.

KyberSlash (Kyber reference C, before the 2024 fix)

// compress a secret coefficient x
t = ((x << d) + KYBER_Q/2) / KYBER_Q;

→ some compilers & WebAssembly: div

Depending on compiler and platform, this became a hardware divide. On many CPUs it finishes faster for some numbers than others, and x here is secret. Researchers recovered keys from it.

This crate

n = (x << d) + 1664
(n * 660 565 714) >> 40

→ WebAssembly: i64.mul · i64.add · i64.shr_u

The same result, ⌊n / 3329⌋, from a multiply and a shift, whose time does not depend on the numbers. Proven equal for every possible input by a test.

A script reads the compiled instructions, x86 and WebAssembly, at every optimisation level, and fails the build if a division or a secret-dependent branch appears. One surprise: for WebAssembly, the compiler keeps even x / 3329 as a real division, while on x86 it quietly turns it into a multiply.

§3

Every measurement, on one ruler

The tester runs an operation millions of times with two kinds of input (one fixed, one random) and asks whether the two timing distributions differ. The answer is Welch's t: under 4.5, nothing detected; over 10, a leak. Each mark below is one committed experiment.

normal build A/A control (cannot leak) deliberately leaky build KeyGen (depends on a public value)

hover a mark for details

The leaky builds are broken on purpose, to prove the instrument can actually see a leak. The red marks on the far right are leaks it caught. The red marks on the left are honest misses: KyberSlash only shows on this laptop's efficiency cores (the same binary reads 2.6 on a performance core and 19 857 on an efficiency core), and its one-bit variant was not detectable on either. A test that passes is evidence, not proof.

§4

Leaks grow. Noise doesn't.

A real difference between the classes makes t grow like √n as measurements pile up. Noise wanders around and stays low. These curves are the tester's own progress lines from the committed runs.

The KyberSlash run is already past 10 000 after its first million samples and then levels off instead of following √n. I have not investigated why. Drift in the CPU over the run is a guess, not a measurement.

§5

Four times the instrument lied

The hardest part was not the cryptography. Four times, the tester reported a leak in code that had none. Each was caught by an A/A control: the same experiment with identical data in both classes, which by construction cannot leak. When the control "leaks" too, the harness is the culprit.

  1. |t| ≈ 122

    Inputs prepared differently per class

    Copying a cached input vs. writing fresh random bytes just before starting the clock: the stores were still draining. Fix: identical preparation and a memory fence.

  2. false leak

    An if class == 0 before timing

    Equal work on both paths, but the branch predictor's history differed per class, and that shifted the timed code's own loop predictions.

  3. false leak

    Branch-free select, still not enough

    Cache and store-buffer state still differed. Fix: the canonical dudect batching. Generate every input first, then time them in a loop with no class-dependent code at all.

  4. |t| ≈ 19

    Only on the efficiency cores

    At ten million samples, correct code "leaked" on the E-cores. The A/A control said 1.8, but it was skipping the random-number work. Once it did exactly the same work, it showed |t| ≈ 11 as well. Fix: copy each batch once more with one memcpy before timing. Lesson: a control is only valid if it does exactly the same work.

How fast

ML-KEM-768 on one performance core of an i7-14700HX, median of 10 000 calls, against RustCrypto's ml-kem. Same inputs for both, outputs checked identical before timing.

§7

How it's checked

  • 240 official NIST ACVP vectors, natively and as WebAssembly in Node
  • byte-for-byte cross-check against RustCrypto's implementation, on random inputs
  • 100 000 property-test cases per property, including literal transcriptions of the spec's pseudocode
  • 7 × 2 optimisation levels × targets scanned for divisions and secret branches (x86-64, wasm32), in CI
  • 52 timing experiments, each next to an A/A control, on two kinds of CPU core, natively and inside V8

Educational code. Not audited. Do not use in production. For real systems use a maintained, audited library.

Every number on this page is generated from the raw results committed in the repository (scripts/site_data.py → data.json). The full story, decisions and mistakes: LEARNING.md.
